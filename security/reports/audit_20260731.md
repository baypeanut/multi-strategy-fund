## Model review
- **low** `backtest/engine.py` (cost loop: `nav = nav0` set before the loop and never reassigned; `trade_value = abs(dw) * nav`): The notional used to size trades and impact costs is frozen at the initial NAV for the entire backtest. The equity curve compounds (`equity = nav0 * (1 + net_ret).cumprod()`), but the cost loop always prices turnover off nav0, so square-root impact is computed on the wrong trade size whenever equity has drifted from its starting value.
  - Impact cost is non-linear in trade value, so on a strategy that grows, per-rebalance costs are systematically understated and `cost_drag_annual` reports a drag lower than the strategy would actually incur. Capacity and sizing decisions made off this number will be too aggressive.
- **low** `backtest/engine.py` (`w = res.weights.reindex(close.columns).fillna(0.0)` and `W.loc[d] = w`): Weights returned by `engine.generate` are accepted verbatim: there is no check on gross exposure, net exposure, per-name concentration, or NaN/inf before they are written into the weight panel and multiplied by returns.
  - The backtest can report performance for a book that would be rejected by the live risk layer (e.g. arbitrary leverage from a mis-scaled optimizer output), so the simulated track record does not correspond to anything the production order path would be allowed to execute.
- **low** `backtest/metrics.py` (cscv_pbo(), `if N < 2 or T < s: return float('nan')`): Insufficient-data conditions return a NaN sentinel rather than raising. Any downstream gate written as a comparison (e.g. `if pbo > threshold: reject`) evaluates False against NaN and therefore admits the strategy, i.e. the overfit check silently fails open when the perf matrix is too small or too sparse after dropna().
  - The PBO figure exists to block overfit configurations from promotion. A silent NaN that reads as 'pass' in a comparison converts a research safeguard into a no-op exactly in the low-data case where overfitting risk is highest, with no error or log to signal that the check did not run.
- **low** `backtest/metrics.py` (cscv_pbo(), `for is_idx in combinations(range(s), s // 2)`): The number of CSCV partitions is C(s, s/2) and grows factorially in the caller-supplied `s`, with no upper bound enforced (s=10 gives 252 iterations, s=40 gives ~1.4e11). Each iteration performs two full DataFrame slice-and-mean operations.
  - If `s` is ever sourced from a config file or job payload that a lower-trust caller can influence, a modest value makes this function run effectively forever and pin a worker, stalling the research/validation pipeline. The absence of any bound on a factorially-growing loop parameter is the defect.
- **high** `config/config.yaml` (agent_governance.mode: paper_flexible, with the E30 comment block above it ("FULL AUTHORITY ... the agent ... applies them ITSELF: no human gate on any path")): The stated control model is that `mode` is "the cage every agent runs inside" and that flipping it "is an owner decision, never an agent's" - but the agent is documented as having unrestricted apply authority over the repo, and this cage is a plain YAML key in that repo. Nothing in this file scopes the agent's write authority to exclude config/config.yaml or the agent_governance block. The same applies to ibkr.enabled, ibkr.execute, ibkr.account, systems.*.enabled and the entire risk: block.
  - A control that the controlled process can rewrite is not a control. The two named compensating mechanisms (pytest-green + git commit per proposal) do not help: a proposal that flips `mode: real_money_locked -> paper_flexible`, sets `ibkr.execute: true`, or widens `max_gross`/`daily_loss_kill` will pass a test suite that reads its limits from this same file, and git revert is after-the-fact. At go-live the plan is to shut the lane "with one line" in this file - that one line is writable by the thing it is meant to shut.
- **medium** `config/config.yaml` (watchdog.auto_restart_gateway: true): An out-of-process cron watchdog automatically restarts a wedged IBKR Gateway, once per realert window, with no check against a halt/kill state. Killing the Gateway is the standard out-of-band way an operator severs the broker connection; this config makes that action self-reversing.
  - Fails open on the outbound-order path. An operator who kills the Gateway to stop order flow during an incident gets it silently brought back up, and the trading process reconnects and resumes syncing. The restart also masks the underlying wedge as a recurring self-heal instead of surfacing it.
- **medium** `config/config.yaml` (ibkr.account: DU0000000 and the comment "The broker module hard-refuses any account not starting with 'DU' ... At real money, human order confirmation gets inserted in core/broker/ibkr_broker.py"): The only barrier between this config and a live account is a string-prefix test on an operator-supplied account id, and the human order-confirmation step is explicitly deferred to a future edit rather than existing now. Whether the prefix check is actually enforced cannot be verified in this file; what is visible here is that the config layer offers no second, independent gate (e.g. a separate live-trading flag that must also be set).
  - A prefix convention is a weak type check: it is defeated by any account id that happens to start with DU, by a broker naming change, or by a single-token edit to `account:`. Combined with the agent's write authority over this file, the entire live-money barrier is one string and one boolean.
- **medium** `config/config.yaml` (alerts.telegram_daily_only: true, digest_hour_utc: 21): All notifications except HALT, halt-clear and backup-failure are batched into a single daily digest. Order rejections, broker auth failures, risk-limit breaches short of a halt, LLM spend-cap exhaustion, and applied agent proposals are therefore invisible for up to ~24 hours.
  - This is a detection-latency defect on the paths that matter most (broker orders and self-applied code changes). An attacker or a malfunctioning agent has a full trading day of cover before anything reaches a human, and the auto-rollback/git-revert remedies depend on someone noticing.
- **low** `config/config.yaml` (ibkr.session_only: true - "A halt-flatten is exempt (risk control)"): The session gate that otherwise blocks all order submission outside US cash hours has a documented bypass for halt-flatten orders. The exemption is described but not bounded here (no cap on size, count, or order type for the exempt path; max_orders_per_sync is documented as a sync fuse).
  - Any exemption from an order-submission guard is a code path that can place orders when the guard says no. If the halt-flatten classification can be reached by an input the process does not fully control, it becomes the way to submit orders into an illiquid overnight book.
- **low** `config/config.yaml` (systems.s5_event: { risk_weight: 0.00, enabled: true } alongside the comment "`enabled` is a real kill switch for every book (E47) ... Off now means the book goes flat and keeps being marked"): S5 is armed (enabled: true) at zero risk weight, so its trading state is governed by a numeric weight rather than by the flag that is documented as the kill switch. The prior incident recorded in this same comment was precisely that config flags did not match trading behaviour.
  - Two independent controls for one book means an operator reading `enabled: true` cannot tell whether the sleeve can take risk, and a change to risk_weight arms it without touching the flag that is audited as the kill switch.
- **medium** `core/alerts.py` (send_telegram: `except Exception: return False`): Every failure of the urgent send path (DNS, TLS, HTTP non-200, malformed token, timeout) is swallowed and collapsed into a bare False, with no log line, no counter, and no state marker. The only signals reserved for the urgent channel are the halt latch, human clear, and backup failure.
  - The alerts that matter most are exactly the ones that vanish without trace. An operator sees no message and has no way to distinguish 'nothing happened' from 'the halt fired and the notification failed'. A misconfigured or revoked token degrades the safety-notification channel indefinitely and silently.
- **medium** `core/alerts.py` (send_telegram: `if not urgent: return False`): A non-urgent call is discarded at the top of the function. It is not queued via queue_note, not recorded, and the False return is indistinguishable from a delivery failure. Any existing caller that passes urgent=False, or any future caller that assumes send_telegram delivers, loses the message entirely.
  - Silent message destruction in the alerting primitive means risk or governor notices can be written by a caller and never reach a human or the digest. The API shape invites the mistake because the drop path returns the same value as a genuine send failure.
- **medium** `core/alerts.py` (maybe_send_daily_digest -> format_daily_digest (`float(state.get('nav0') ...)`, `halt.get('ts')`, `f"${ibk['nav']:,.0f}"`)): format_daily_digest performs unguarded float() conversions and attribute/format operations on values pulled straight out of the state dict, and maybe_send_daily_digest calls it with no try/except. A non-numeric nav0 or system equity raises ValueError; a halt_latched or ibkr entry that is a string rather than a dict raises AttributeError; a non-numeric ibkr['nav'] raises on the format spec.
  - The module contract is 'alerting must never take the trading loop down', and every other path honours it. This one does not: corrupted or partially written persisted state turns the once-a-day digest call into an exception that propagates into the trading loop.
- **low** `core/alerts.py` (format_daily_digest: `f"IBKR {ibk.get('account', '')}: NAV ${ibk['nav']:,.0f} ..."`): The broker account identifier, NAV, position count, and per-system equity are transmitted in cleartext-to-the-operator's-Telegram, i.e. through a third-party messaging provider, on a daily basis.
  - The account number plus NAV is the most sensitive non-credential data the platform holds. Telegram bot messages traverse and are retained by an external service; if the chat ID is ever misconfigured or the bot is added to the wrong chat, the account identifier goes with it. This may be an accepted trade-off, but it is an unredacted disclosure of account identity to an outside system.
- **low** `core/alerts.py` (queue_note / format_daily_digest 'Notes:' block, and `actions[:3]` from state['last_actions']): Note and governor-action text is copied verbatim from callers into persisted state and then into an outbound message with no redaction or pattern filtering. There is no scrubbing of anything resembling a token, key, or URL containing credentials before the content leaves the process.
  - The alerting module is the one place where internal strings cross the process boundary to a third party and are also written to durable state. A caller that queues an exception string - for example one containing a request URL with an embedded API token, as this very module constructs - would leak the secret both to disk and to Telegram. The absence of a scrub step in the single egress choke point is the defect.
- **low** `core/alerts.py` (send_telegram: `f"https://api.telegram.org/bot{token}/sendMessage"`): The TELEGRAM_BOT_TOKEN value from the environment is interpolated into the request URL without validation. Whitespace, control characters, or path separators in the env value produce a malformed URL or an unintended request path.
  - Control characters in a URL are rejected by http.client, so request splitting is not reachable here, and the resulting exception is swallowed - but a token containing a stray path separator would silently direct the request at a different API path, and the failure is invisible because of the bare except. A truthiness check (`if not token`) does not catch a whitespace-only or malformed value.
- **medium** `core/broker/costs.py` (estimate(): `participation = (trade_value / adv) if adv > 0 else 0.0`): When ADV is missing, zero, or negative, the market-impact term silently collapses to zero instead of raising or falling back to a conservative penalty. The guard fails open: the least liquid or least-well-known names get the cheapest modeled execution.
  - Impact is the dominant cost term for large orders in thin names. A data gap in the ADV field (new listing, halted symbol, bad vendor row) makes a backtest or pre-trade check report near-zero slippage, so size limits and expected-cost gates keyed off this number can be passed by exactly the orders that should be blocked. There is no log or signal that the input was degraded.
- **low** `core/broker/costs.py` (estimate(): `math.sqrt(max(participation, 0.0))`): The docstring states trade_value is the absolute notional, but this is never enforced. A negative trade_value yields a negative participation, which max() clamps to 0.0, producing zero impact rather than an error.
  - A sign-convention mistake in a caller (e.g. passing a signed sell notional) is silently converted into a zero-cost trade instead of surfacing as an exception, so the wrong-sign bug reaches the fill path undetected.
- **low** `core/broker/costs.py` (borrow_cost(self, short_value, days=1.0)): `days` is not validated; a negative value produces a negative borrow cost, i.e. a credit to the position.
  - A negative or corrupted holding-period value turns a carrying cost into P&L, inflating the modeled return of short positions rather than failing loudly.
